## 5. G4 launch routine

1. The Pi is up and its clock is right: `ssh rpi400@rpi400-server date -u`.
1b. On the launch commit: full tests (`scripts/test_cpu.py`) and the golden compare pass (rule added 2026-10-20, [test levels](test-levels.md)).
2. Any checkpoint the job needs is staged on the VM first (maintenance boot with the user's OK, scp, SHA check on the VM).
3. From the launch worktree, on a pushed commit, dry run first:

   ```sh
   cd runs/.scratch/srm-hard-launch && git fetch origin && git checkout --detach origin/yx
   scripts/g4/submit.sh run --notebook notebooks/experiments/<name>.ipynb \
     --commit $(git rev-parse HEAD) --timeout-min 165 --max-run-minutes 180 --dry-run
   ```

   Then the same command without `--dry-run`. The GCE max run duration must be at least `--max-run-minutes`.
4. On STOCKOUT: retry every 4 min with a fresh job ID, at most 15 attempts (`runs/.scratch/retry-launch.sh WORKTREE NOTEBOOK 165 180 FIRST_ATTEMPT`). On preemption: fresh run, at most 3 relaunches.
5. Set the run queue row to `running`. Live epoch times: `~/AAI3001-CVDL/runs-out/<job>/checkpoints/<job>/epoch_timing.csv` on the VM.
6. After the end: copy from the Pi, check Pi = PC SHA-256, evaluate (standard-256 + hard-256), update the run queue.

## 7. Rules learned today

- Decision rules: use paired-difference intervals or AUC. Do not use "model intervals do not overlap" or misses at one cut-off (confounded by score bias).
- Timing pilots: no per-step GPU synchronising callbacks (the arm A pilot under-measured speed by up to 2.5x). Use `pilot=true` and the warm epoch time; the real G4 epoch time is in `~/AAI3001-CVDL/runs-out/<job>/checkpoints/<job>/epoch_timing.csv` on the VM.
- SRM models on the PC: evaluate with `--set rocm_conv1_fix=off --set eval_batch_size=32`.
- G4: one run per boot; the Pi must be online before a paid boot; launch only from the clean launch worktree, dry run first.
